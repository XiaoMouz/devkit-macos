# DevKit 交付计划

## 当前阶段

用户已明确启动开发。当前已形成 0.1.0 自用版本，包含 72 个工具引擎、原生工作空间与 App Intents。实际范围见 [实现记录](implementation-status.md)，检查结果见 [验收记录](verification.md)。前一轮已回滚实现不作为证据。

需求讨论与文档基线已先行完成；本轮依据用户随后发出的“开始写代码完成项目吧”进入开发。以下阶段表保留为目标，不能反推所有退出条件已满足。

## 交付顺序

| 阶段 | 范围 | 交付物与退出条件 |
| --- | --- | --- |
| D0 设计 | 本组文档与待确认项 | 需求、模块清单、交互、视觉、系统可行性计划、测试标准形成一致基线 |
| D1 视觉评审 | 首页、转换、生成、对比、预览、设置、Spotlight 结果 | 先评审静态稿/交互草图；确认原生风格、操作位置与窄窗口表现 |
| T0 技术验证 | Spotlight A/B、原生玻璃、编辑器尺寸、模块边界 | 在进入开发阶段后，用最小验证场景收集系统证据；失败时修订方案 |
| B1 核心日用 | 14 个模块和工作空间 | 收藏、搜索、标签、复制、编辑器、系统适配可用，完成首批模块验收 |
| B2 开发数据 | 新增 27 个模块 | 累计 41 个模块；复杂解析和不同数据语义有清晰约束 |
| B3 前端资源 | 新增 16 个模块 | 累计 57 个模块；图像和预览能力有资源及权限边界 |
| B4 格式与网络 | 新增 15 个模块 | 累计 72 个模块；显式联网、隔离和格式依赖通过各自验证 |
| R 发布准备 | 已完成批次的公开交付 | 安装、签名、更新策略、支持范围、隐私和依赖说明与实际行为一致 |

分批编号表示实施先后，不是未经评估的日期承诺。可以在 B1 后先自用；后续是否以某个完成批次开始公开发布，由实际质量与发布目标决定。每次发布只宣传该版本已验收的能力。

## 第一批明确范围

Base64、URL 编解码、JSON、哈希摘要、随机字符串、UUID、文本对比、命名/大小写、文本行处理、文本统计、时间戳、URL 解析、查询参数、颜色转换。

先以 Base64 作为纵向样例串通模块、主窗口、状态、复制和系统动作；样例通过后再复制结构。不能提前为 72 个工具创建大量占位页面，掩盖公共结构还未验证的问题。

## 技术验证的失败处理

- 若 B 无法按原命令成立，保留其问题证据，列出系统允许的最接近方案，再确定需求调整；不得静默只交付 A。
- 若玻璃与自定义编辑器出现显示问题，先恢复系统控件行为，再评估必要的定制。
- 若某格式依赖无法满足精度、许可证或资源限制，先调整该模块方案，不向其他工具传播临时绕过。
- 若取消不能真正停止危险或过量工作，先完成隔离机制，不将该工具标记可用。

## 每批交付内容

包括可运行应用、变更说明、模块完成清单、对应测试结果、主窗口与系统集成验证、性能样本和已知限制。文档随行为变化更新，不积累一份过期的“最初设计”。

每批只在完成自身验收后扩展下一批范围。共享组件的修改需要回归受影响模块，不为无关工具反复运行全部昂贵任务。

## 公开发布的待定决策

待选择：直接下载、Mac App Store 或两者；是否开源及许可证；是否收费；支持哪些硬件架构；是否需要应用内更新与签名分发渠道；初次公开发布的语言范围。

这些选择不妨碍文档阶段确定模块和交互，但影响沙箱、文件权限、网络能力、打包和发布验证，不能在发布前才临时处理。

## 开发开始前的文档检查

需求和视觉方向已经讨论清楚；每个计划工具能映射到模块；默认行为与用户确认区分；A/B 的待验证点完整；测试标准能识别“看起来可用但实际上没完成”的情况。该进入条件已由用户后续开发指令满足；系统验证的阻塞仍按验收记录跟踪。
